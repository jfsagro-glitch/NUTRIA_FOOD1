## Спринт 1 — Качество данных и базовый UX (приоритет: ВЫСОКИЙ)

Быстрые доработки с высоким impact, каждая — 2-4 часа работы.

### 1.1 DRI-прогресс-бары в нутриентах
**Что:** В блоке «Все нутриенты» рядом с каждым значением — прогресс-бар к суточной норме (DRI).  
**Почему:** Сейчас цифры висят в вакууме. 12 мг железа — это хорошо или плохо? Прогресс-бар отвечает мгновенно.  
**Как:**
- Добавить в `server.ts` объект `DRI_REFERENCE` с нормами по полу:
  ```
  Клетчатка:        38г (м) / 25г (ж)
  Кальций:          1000 мг
  Железо:           8 мг (м) / 18 мг (ж)
  Калий:            3400 мг (м) / 2600 мг (ж)
  Витамин D:        15 мкг
  Витамин B12:      2.4 мкг
  Магний:           400 мг (м) / 310 мг (ж)
  Натрий (лимит):   ≤ 2300 мг
  Сахар (лимит):    ≤ 50 г
  Насыщ. жиры:      ≤ 22 г
  ```
- `GET /api/diary/:date` добавить поле `dri[]` с `{ name, consumed, target, unit, isLimit }`.
- В ClientApp.tsx: нутриент с `isLimit: true` красится в красный при превышении; обычный — зелёный при 80-120%, серый при недоборе.
- Пол/возраст брать из `UserProfile` (создать если нет, дефолт: мужчина 30 лет).

**Файлы:** `server.ts`, `ClientApp.tsx`, `schema.prisma` (добавить `UserProfile`)

### 1.2 Nutri-Score в карточках продуктов
**Что:** Значок A/B/C/D/E на карточках в результатах поиска и в записях дневника.  
**Почему:** Пользователь сразу видит качество продукта без анализа чисел. Конкурентное преимущество — у большинства российских приложений этого нет.  
**Как:**
- Функция `calcNutriScore(product)` в `server.ts` (per 100g):
  ```
  Negative: ккал (0-10pt) + насыщ.жиры (0-10pt) + сахар (0-10pt) + натрий (0-10pt)
  Positive: клетчатка (0-5pt) + белок (0-5pt)
  Score = negative - positive
  A: ≤ -1 | B: 0-2 | C: 3-10 | D: 11-18 | E: ≥ 19
  ```
- Добавить `nutriScore` в ответ `/api/products/search` и `/api/diary/:date`.
- В UI: цветной бейдж (зелёный A → красный E) в углу карточки продукта.

**Файлы:** `server.ts`, `ClientApp.tsx`

### 1.3 Inline-редактирование граммов в дневнике
**Что:** Клик на число граммов в записи дневника — поле становится редактируемым inline. Enter/blur сохраняет.  
**Почему:** Сейчас если ошибся в граммах — нужно удалить запись и добавить заново. Это раздражает.  
**Как:**
- Добавить `PATCH /api/diary/entries/:entryId` с телом `{ grams: number }`.
- В ClientApp.tsx: вместо статичного `<span>{entry.grams}г</span>` — компонент `<InlineGramsInput>`, который при клике показывает `<input type="number">`, при blur/Enter вызывает PATCH и обновляет локальный state.

**Файлы:** `server.ts`, `ClientApp.tsx`

## Спринт 2 — Умный дневник (приоритет: СРЕДНИЙ)

### 2.1 Per-meal kcal-цели и профили питания ✅
**Что:** Каждая карточка приёма пищи показывает прогресс к *своему* лимиту, а не просто суммируется в общее.  
**Почему:** Тяжёлый ужин vs лёгкий завтрак — разные цели. Сейчас все приёмы пищи равнозначны.  
**Как реализовано** (по аналогии с 1.1 DRI-барами — клиентский профиль, без новой модели в Prisma):
- `UserProfileSettings.mealDistribution` (поле в клиентском профиле `ClientApp.tsx`, хранится в `localStorage`, как и весь остальной профиль/цели) с дефолтом `{BREAKFAST:25, LUNCH:35, DINNER:30, SNACK:10}`.
- 3 предустановленных профиля (`MEAL_DISTRIBUTION_PRESETS`) + ручная правка процентов: Стандартный / Средиземноморский / OMAD. Выбираются в шторке «Профиль и цели».
- `mealTarget` для каждого приёма пищи считается на клиенте: `calorieGoal × pct / 100` — без изменений `server.ts`/`schema.prisma`.
- В карточках Завтрак/Обед/Ужин/Перекус: мини-прогресс-бар `съедено / цель приёма` под названием продуктов.

**Файлы:** `ClientApp.tsx`

---

### 2.2 Физическая активность — трекер тренировок ✅
**Что:** Логирование тренировок с расчётом потраченных ккал. Сожжённые калории увеличивают дневной бюджет на кольце калорий.  
**Почему:** Без физической активности невозможно считать энергетический баланс.  
**Как реализовано:**
- Модель `ActivityLog` в Prisma: `{ userId, date, activityName, durationMinutes, caloriesBurned }` (+ in-memory fallback для режима без БД).
- Расчёт `kcal = MET × weightKg × (durationMinutes / 60)` считается на клиенте (вес берётся из профиля в localStorage, как и DRI/цели) — таблица `ACTIVITY_MET_TABLE` из 28 активностей в `ClientApp.tsx`. Сервер только хранит готовое значение.
- `POST /api/activities`, `GET /api/activities/:date`, `DELETE /api/activities/:id`.
- В дневнике: новый блок «Активность» с кнопкой «+ Тренировка» (шторка выбора активности + длительности с превью расхода), список тренировок за день с удалением.
- Кольцо калорий: цель = `calorieGoal + Σ caloriesBurned за день`, под целью подпись «+N от тренировок».

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`

---

### 2.3 Трекер веса тела ✅
**Что:** Запись веса раз в день, история в виде графика с линией цели.  
**Почему:** Нутрициолог должен видеть динамику веса клиента. Пользователь видит результат.  
**Как реализовано:**
- Модель `WeightLog`: `{ userId, date, weightKg }`, `@@unique([userId, date])` — повторная запись за тот же день обновляет значение (upsert), без дублей. In-memory fallback (`Map<userId, Map<dateKey, weightKg>>`) для режима без БД.
- `POST /api/weight` (upsert по дню), `GET /api/weight/history?days=30`.
- В UI (экран «Профиль» в `ClientApp.tsx`): карточка «Вес» с полем ввода + кнопкой «Записать», hand-rolled SVG sparkline-график (recharts в проекте на самом деле нет — решили не добавлять новую зависимость, нарисовали график вручную, по аналогии с кольцом калорий). При сохранении веса обновляется и `profileSettings.weightKg` — значение сразу используется в расчётах MET/BMR/TDEE.
- В CRM (`crm-routes.ts` → `GET /api/crm/clients/:clientId/weight-history`, `CrmApp.tsx` → таб «Вес»): нутрициолог видит график и список записей веса клиента (без новой зависимости — тот же hand-rolled SVG-подход).

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`, `crm-routes.ts`, `CrmApp.tsx`

## Спринт 3 — Рецепты и планирование (приоритет: СРЕДНИЙ)

### 3.1 Импорт рецептов по URL ✅
**Что:** Пользователь вставляет ссылку на рецепт с любого кулинарного сайта — приложение извлекает ингредиенты и КБЖУ.  
**Почему:** Большинство крупных кулинарных сайтов (AllRecipes, Foodnetwork, BBC GoodFood и др.) используют schema.org/Recipe разметку — это парсится автоматически.  
**Как реализовано:**
- `POST /api/recipes/import-url` — fetch URL (с таймаутом и User-Agent), ищет `<script type="application/ld+json">` через `extractRecipeJsonLd()` (поддерживает `@graph`, массивы, `@type:"Recipe"`).
- Парсит `name` и `recipeIngredient[]` (свободный текст на любых единицах — стаканы, унции, штуки).
- Список ингредиентов переводится в граммы и канонические названия одним AI-вызовом (`generateAI` + `parseAiJsonPayload`/`unwrapAiItemsArray`, по тому же паттерну, что и `/api/voice/parse`), затем каждый ингредиент независимо матчится к `Product` через `searchProductsEngine(..., { fast: true })`.
- Эндпоинт **только превью** — не создаёт `Recipe` напрямую: клиент получает `{ name, ingredients }`, отфильтровывает сматченные и передаёт в уже существующий флоу «Создать блюдо» (`dishName`/`dishIngredients`/`submitDish()`), который и делает фактическое сохранение через уже существующий `POST /api/recipes`. Это избегает дублирования логики матчинга/сохранения.
- В UI: кнопка «Импортировать рецепт по ссылке» (таб «Мои блюда») → `BottomSheet` с полем URL → при успехе открывается стандартный экран создания блюда с предзаполненными ингредиентами.

**Файлы:** `server.ts` (`extractRecipeJsonLd`, `POST /api/recipes/import-url`), `src/ClientApp.tsx` (кнопка, `BottomSheet`, `importRecipeFromUrl()`)

**Ограничения тестирования:** в текущей среде разработки нет AI-ключей и заблокирован внешний сетевой доступ, поэтому AI-декомпозиция и реальный fetch внешних страниц не протестированы вживую "до конца" (real URL → real AI). Все синхронные пути проверены живым smoke-тестом: 401 (без авторизации), 400 (некорректный URL), 422 (страница без `schema.org/Recipe` разметки), 502 (страница недоступна). Логика декомпозиции и матчинга переиспользует уже проверенный код `/api/voice/parse`.

### 3.2 Пользовательские рецепты (ручное создание) ✅
**Что:** Создать рецепт вручную: название, фото, список ингредиентов из базы, количество порций. КБЖУ считается автоматически.  
**Почему:** Домашняя кухня. Пользователь один раз вводит рецепт борща — потом добавляет в дневник в 2 тапа.  
**Как реализовано:** обнаружено, что функциональность уже была полностью реализована ранее (до этого спринта) — не требовала новых правок:
- Модели `Recipe`/`RecipeIngredient` в `schema.prisma`, полный CRUD `POST/GET/PATCH/DELETE /api/recipes` в `server.ts`.
- В `ClientApp.tsx`: таб «Мои блюда» со списком сохранённых рецептов, экран создания/редактирования с ручным подбором ингредиентов из базы продуктов и AI-автозаполнением состава (переиспользует `/api/voice/parse`).
- КБЖУ рецепта считается на клиенте суммированием ингредиентов по весу.

**Файлы:** `server.ts`, `prisma/schema.prisma`, `src/ClientApp.tsx` (без изменений в этом спринте)

## Спринт 4 — Экспорт, аналитика и CRM (приоритет: СРЕДНИЙ/НИЗКИЙ)

### 4.1 Экспорт личных данных ✅
**Что:** `GET /api/export` возвращает zip с diary.json + custom_foods.json + weight_history.json.  
**Почему:** Пользователи больше доверяют приложению, из которого могут забрать свои данные. Обязательно для GDPR.  
**Как реализовано:**
- `GET /api/export` (dual-path: in-memory и Prisma) собирает `Meal+MealItem+Product` пользователя, его кастомные продукты (`source: "user"`), `WeightLog` и `ActivityLog`, упаковывает в zip через пакет `archiver` (v8, ESM-классы `ZipArchive` — у текущей мажорной версии нет классической функции-фабрики, поэтому используется `new ZipArchive(...)`).
- Архив отдаётся напрямую как `Content-Disposition: attachment` без промежуточного сохранения на диск.
- В UI: кнопка «Скачать архив» в разделе «Настройки» профиля (простая ссылка `<a href="/api/export" download>`, без JS-обработки blob — cookie-аутентификация работает на обычной навигации).

**Файлы:** `server.ts` (`GET /api/export`), `src/ClientApp.tsx` (кнопка в «Настройках»), `package.json` (+`archiver`)

**Проверено:** живым smoke-тестом (login → добавление веса → скачивание → проверка валидности zip и содержимого `weight_history.json`/`diary.json` через `unzip -l`/`unzip -p`).

### 4.2 Аналитика за неделю/месяц ✅
**Что:** Экран «Аналитика» — средние ккал и КБЖУ, сколько дней выполнена цель, тренды.  
**Почему:** Нутрициолог в CRM должен видеть прогресс клиента за период, а не листать день за днём.  
**Как реализовано:**
- `GET /api/crm/clients/:clientId/analytics?days=` (CRM-only, без in-memory фоллбэка — по конвенции `crm-routes.ts`) агрегирует `Meal+MealItem+Product` и `WeightLog` клиента за период.
- Возвращает `{ days, trackedDays, avgCalories, avgProtein, avgFat, avgCarbs, calGoalHitDays, goals, weightTrend }`.
- В CRM: вкладка «Статистика» в профиле клиента — переключатель периода (7/30/90 дн.), карточки со средними значениями и SVG-спарклайн динамики веса (тот же hand-rolled подход, что и в `WeightTab`).

**Файлы:** `crm-routes.ts` (эндпоинт), `src/CrmApp.tsx` (`AnalyticsTab`)

### 4.3 Список покупок из плана питания (CRM) ✅
**Что:** Нутрициолог составляет недельный план блюд для клиента → автоматически генерируется список покупок.  
**Почему:** Это главная ценность CRM для платящих нутрициологов.  
**Как реализовано:**
- Новые модели `MealPlan` / `MealPlanItem` в `schema.prisma` — план содержит позиции `{ dayOfWeek, mealType, productId, amountGrams }` (та же структура, что у `MealItem` дневника), без отдельной модели рецептов плана — нутрициолог подбирает продукты напрямую через существующий поиск `/api/products/search`.
- CRUD: `GET/POST /api/crm/clients/:clientId/meal-plans`, `GET/DELETE /api/crm/meal-plans/:planId` (с проверкой владения по `nutritionistId`).
- `POST /api/crm/meal-plans/:planId/shopping-list` — суммирует граммовки одинаковых продуктов по всем позициям плана и группирует по категории. Категория определяется локальной эвристикой по ключевым словам в названии (без AI — в `Product` нет поля категории, а для списка покупок важна стабильность, а не точность), фоллбэк-категория «Прочее».
- В CRM: вкладка «Меню» — список планов клиента, форма создания плана (день недели + приём пищи + поиск продукта + граммы), кнопка «Список покупок» с группированным выводом.

**Файлы:** `prisma/schema.prisma` (`MealPlan`, `MealPlanItem`), `crm-routes.ts` (CRUD + shopping-list), `src/CrmApp.tsx` (`MealPlansTab`)

**Ограничения тестирования:** CRM-роуты работают только с реальной БД (без in-memory фоллбэка, по существующей конвенции проекта), а в текущей среде разработки нет `DATABASE_URL` — поэтому эндпоинты проверены только `tsc --noEmit`/`vite build` и сверкой со структурой уже проверенных CRM-эндпоинтов (`weight-history`, `diary`).

### T1 — Vitest + supertest ✅

**Как реализовано:**
- `server.ts` был структурно одной гигантской функцией `startServer()`, которая одновременно настраивала Express-приложение, регистрировала Vite middleware/статику и вызывала `app.listen()` — `app` никуда не экспортировался, поэтому импортировать его в тестах было невозможно. Разделил на:
  - `export async function createApp(): Promise<express.Express>` — настраивает `app` (все маршруты, CRM, телеграм-бот, глобальный error handler) и возвращает его без вызова `.listen()`.
  - `async function startServer()` — тонкая обёртка: `const app = await createApp(); app.listen(PORT, ...)`.
  - Добавлена ветка `process.env.NODE_ENV === "test"` в блок Vite/статика — в тестах не нужны ни Vite middleware, ни раздача `dist/` (только `/api/*`).
  - Автозапуск на верхнем уровне файла обёрнут в `if (process.env.NODE_ENV !== "test")`, чтобы импорт `createApp` в тестах не поднимал реальный сервер на порту.
- Vitest сам устанавливает `NODE_ENV=test`, поэтому тесты автоматически попадают в in-memory режим (нет `DATABASE_URL` в среде разработки) — это совпадает с единственным режимом, который можно проверить без реальной БД.
- `tests/api.test.ts`: 10 тестов на `/api/auth/login`+`/api/auth/me`, `/api/weight`+`/api/weight/history`, `/api/export` (включая проверку ZIP-сигнатуры `PK` в бинарном теле ответа) и синхронные пути `/api/recipes/import-url` (401/400, не требующие сети). Тесты CRM-эндпоинтов и AI-путей (фото/голос/поиск) не добавлены — они либо требуют реальной БД (CRM, по конвенции без in-memory фоллбэка), либо реальных AI-провайдеров.

### T2 — Rate limiting ✅

**Как реализовано:**
- Два лимитера на базе `express-rate-limit`, оба регистрируются в `createApp()` сразу после `express.json()`/`cookieParser()`, до объявления маршрутов:
  - Общий — `app.use("/api", apiLimiter)`: 300 запросов / 15 минут на IP, покрывает все `/api/*`.
  - Строгий — навешан только на эндпоинты входа/регистрации (`/api/auth/login`, `/api/crm/auth/login`, `/api/crm/auth/register`, `/api/onboard/:token/login`): 20 запросов / 15 минут на IP — защита от брутфорса пароля у CRM-логина.
- Оба лимитера используют `skip: () => process.env.NODE_ENV === "test"`, чтобы не мешать тестам (Vitest сам выставляет `NODE_ENV=test`).
- В `tests/api.test.ts` добавлен тест, который на время теста явно выставляет `NODE_ENV=development`, прогоняет 25 запросов к `/api/auth/login` и проверяет, что после 20-го лимитер отдаёт `429`.
- Проверено также вживую (`tsx server.ts` + `curl`) — на ответах видны заголовки `RateLimit-Limit`/`RateLimit-Remaining`/`RateLimit-Policy`.

**Файлы:** `server.ts` (импорт `express-rate-limit`, два лимитера), `tests/api.test.ts`, `package.json`

### T3 — Валидация входящих данных (zod) ✅

**Как реализовано:**
- Новый общий модуль `validation.ts`: middleware-фабрика `validateBody(schema)` — вызывает `schema.safeParse(req.body)`, при ошибке сам отдаёт `400` с `{ error, details: [{ path, message }] }`, при успехе подменяет `req.body` на уже провалидированные/приведённые к типу данные (`z.coerce.number()` → реальное число, `.trim()` применён, дефолты подставлены) и передаёт управление обработчику маршрута.
- В `validation.ts` собраны zod-схемы для всех POST/PATCH-эндпоинтов `server.ts` (клиентский дневник, фото, голос, рецепты) и `crm-routes.ts` (CRM-регистрация/логин, клиенты, заметки, рекомендации, консультации, планы питания, онбординг).
- Заменены ручные проверки вида `if (!field) return res.status(400)...` на `validateBody(schema)` в 17 маршрутах `server.ts` и 12 маршрутах `crm-routes.ts` — обработчики теперь читают уже проверенные поля напрямую из `req.body` без повторной нормализации (`String(...)`, `Number(...)` и т.п. в основном убраны там, где их теперь делает zod).
- **Сознательно ужесточено поведение** там, где старая ручная проверка имела пробел (это исправление пробела в валидации, а не смена бизнес-логики):
  - `/api/diary/goals` — раньше falsy-проверка (`!calories`) пропускала отрицательные значения (`!(-5)` → `false`); теперь `.positive()`.
  - `/api/diary/add`, `/api/diary/quick-add` — `type`/`mealType` теперь проверяются по `z.enum(["BREAKFAST","LUNCH","DINNER","SNACK","WATER"])` вместо произвольной строки.
  - `/api/crm/auth/register` — добавлены `.email()` и `.min(6)` на пароль (раньше пароль вообще не валидировался по формату/длине).
- **Сознательно не мигрированы на zod** (оставлена прежняя ручная логика, так как zod не покрывает этот случай тривиально):
  - `/api/recipes/import-url` — формат/протокол URL (`new URL()` + allowlist `http:`/`https:`) проверяется кодом, zod-схема только гарантирует непустую строку.
  - `/api/crm/clients/:clientId/analyses` — multer file-upload, основной payload — это файл, а не JSON body.
- Подтверждено грепом, что клиентский код (`ClientApp.tsx`, `CrmApp.tsx`) не читает текст `error` для отображения — только статус-коды, поэтому смена формулировок ошибок при миграции безопасна.
- `tests/api.test.ts`: добавлены 3 новых теста на ужесточённую валидацию — отрицательная калорийность в `/api/diary/goals` (400), отсутствующий `transcript` в `/api/voice/parse` (400), некорректный тип `weightKg` в `/api/weight` (400). Полный набор — 14 тестов, все проходят.
- Проверено: `tsc --noEmit` без ошибок, `vitest run` — 14/14, `vite build` — собирается, живой смоук (`tsx server.ts` + `curl`) на `/api/diary/goals` подтвердил и 400 на невалидных данных, и 200 с корректным сохранением на валидных.

**Файлы:** `validation.ts` (новый), `server.ts`, `crm-routes.ts`, `tests/api.test.ts`
