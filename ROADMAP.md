## Спринт 1 — Качество данных и базовый UX (приоритет: ВЫСОКИЙ)

Быстрые доработки с высоким impact, каждая — 2-4 часа работы.

### 1.1 DRI-прогресс-бары в нутриентах
**Что:** В блоке «Все нутриенты» рядом с каждым значением — прогресс-бар к суточной норме (DRI).  
**Почему:** Сейчас цифры висят в вакууме. 12 мг железа — это хорошо или плохо? Прогресс-бар отвечает мгновенно.  
**Как:**
- Добавить в `server.ts` объект `DRI_REFERENCE` с нормами по полу:
  ```
  Клетчатка:        38г (м) / 25г (ж)
  Кальций:          1000 мг
  Железо:           8 мг (м) / 18 мг (ж)
  Калий:            3400 мг (м) / 2600 мг (ж)
  Витамин D:        15 мкг
  Витамин B12:      2.4 мкг
  Магний:           400 мг (м) / 310 мг (ж)
  Натрий (лимит):   ≤ 2300 мг
  Сахар (лимит):    ≤ 50 г
  Насыщ. жиры:      ≤ 22 г
  ```
- `GET /api/diary/:date` добавить поле `dri[]` с `{ name, consumed, target, unit, isLimit }`.
- В ClientApp.tsx: нутриент с `isLimit: true` красится в красный при превышении; обычный — зелёный при 80-120%, серый при недоборе.
- Пол/возраст брать из `UserProfile` (создать если нет, дефолт: мужчина 30 лет).

**Файлы:** `server.ts`, `ClientApp.tsx`, `schema.prisma` (добавить `UserProfile`)

### 1.2 Nutri-Score в карточках продуктов
**Что:** Значок A/B/C/D/E на карточках в результатах поиска и в записях дневника.  
**Почему:** Пользователь сразу видит качество продукта без анализа чисел. Конкурентное преимущество — у большинства российских приложений этого нет.  
**Как:**
- Функция `calcNutriScore(product)` в `server.ts` (per 100g):
  ```
  Negative: ккал (0-10pt) + насыщ.жиры (0-10pt) + сахар (0-10pt) + натрий (0-10pt)
  Positive: клетчатка (0-5pt) + белок (0-5pt)
  Score = negative - positive
  A: ≤ -1 | B: 0-2 | C: 3-10 | D: 11-18 | E: ≥ 19
  ```
- Добавить `nutriScore` в ответ `/api/products/search` и `/api/diary/:date`.
- В UI: цветной бейдж (зелёный A → красный E) в углу карточки продукта.

**Файлы:** `server.ts`, `ClientApp.tsx`

---

### 1.3 Inline-редактирование граммов в дневнике
**Что:** Клик на число граммов в записи дневника — поле становится редактируемым inline. Enter/blur сохраняет.  
**Почему:** Сейчас если ошибся в граммах — нужно удалить запись и добавить заново. Это раздражает.  
**Как:**
- Добавить `PATCH /api/diary/entries/:entryId` с телом `{ grams: number }`.
- В ClientApp.tsx: вместо статичного `<span>{entry.grams}г</span>` — компонент `<InlineGramsInput>`, который при клике показывает `<input type="number">`, при blur/Enter вызывает PATCH и обновляет локальный state.

**Файлы:** `server.ts`, `ClientApp.tsx`

---

### 1.4 Quick Add — быстрое добавление без поиска
**Что:** В шторке добавления еды добавить таб «Быстро» — поля: название + ккал + опционально КБЖУ.  
**Почему:** Домашняя еда, кафе без меню, «примерно съел кашу» — не надо искать продукт в базе.  
**Как:**
- Добавить `POST /api/diary/quick-add` с `{ date, mealType, label, calories, protein?, fat?, carbs? }`.
- В `DiaryEntry` добавить `isQuickAdd Boolean @default(false)` + `quickAddLabel String?`.
- В UI: третий таб в BottomSheet «Быстро» с минимальной формой. В списке дневника Quick Add-записи отображаются с иконкой «молния».

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`

## Спринт 2 — Умный дневник (приоритет: СРЕДНИЙ)

### 2.1 Per-meal kcal-цели и профили питания ✅
**Что:** Каждая карточка приёма пищи показывает прогресс к *своему* лимиту, а не просто суммируется в общее.  
**Почему:** Тяжёлый ужин vs лёгкий завтрак — разные цели. Сейчас все приёмы пищи равнозначны.  
**Как реализовано** (по аналогии с 1.1 DRI-барами — клиентский профиль, без новой модели в Prisma):
- `UserProfileSettings.mealDistribution` (поле в клиентском профиле `ClientApp.tsx`, хранится в `localStorage`, как и весь остальной профиль/цели) с дефолтом `{BREAKFAST:25, LUNCH:35, DINNER:30, SNACK:10}`.
- 3 предустановленных профиля (`MEAL_DISTRIBUTION_PRESETS`) + ручная правка процентов: Стандартный / Средиземноморский / OMAD. Выбираются в шторке «Профиль и цели».
- `mealTarget` для каждого приёма пищи считается на клиенте: `calorieGoal × pct / 100` — без изменений `server.ts`/`schema.prisma`.
- В карточках Завтрак/Обед/Ужин/Перекус: мини-прогресс-бар `съедено / цель приёма` под названием продуктов.

**Файлы:** `ClientApp.tsx`

---

### 2.2 Физическая активность — трекер тренировок
**Что:** Логирование тренировок с расчётом потраченных ккал. Реальные данные в поле «Сожжено» на главном экране.  
**Почему:** Сейчас «Сожжено» всегда 0 или захардкожено. Без физической активности невозможно считать энергетический баланс.  
**Как:**
- Новая модель `ActivityLog` в Prisma: `{ date, activityName, durationMinutes, caloriesBurned }`.
- Расчёт: `kcal = MET × weightKg × (durationMinutes / 60)`. MET-значения — встроенная таблица (~50 активностей).
- `POST /api/activities`, `GET /api/activities/:date`.
- В дневнике: новый блок «Активность» с кнопкой «+ Тренировка», список активностей за день, суммарные потраченные ккал.
- На главном экране: «Сожжено» в кольце = `ActivityLog.sum(caloriesBurned) for date`.

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`

---

### 2.3 Трекер веса тела
**Что:** Запись веса раз в день, история в виде графика с линией цели.  
**Почему:** Нутрициолог должен видеть динамику веса клиента. Пользователь видит результат.  
**Как:**
- Модель `WeightLog`: `{ userId, date, weightKg }`.
- `POST /api/weight`, `GET /api/weight/history?days=30`.
- В UI: отдельная карточка «Вес» на экране профиля с графиком (recharts LineChart уже есть в проекте) и кнопкой «Записать вес сегодня».
- В CRM нутрициолога: вес клиента виден в профиле.

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`, `AppWithCrm.tsx`

## Спринт 3 — Рецепты и планирование (приоритет: СРЕДНИЙ)

### 3.1 Импорт рецептов по URL
**Что:** Пользователь вставляет ссылку на рецепт с любого кулинарного сайта — приложение извлекает ингредиенты и КБЖУ.  
**Почему:** Большинство крупных кулинарных сайтов (AllRecipes, Foodnetwork, BBC GoodFood и др.) используют schema.org/Recipe разметку — это парсится автоматически.  
**Как:**
- `POST /api/recipes/import-url` — fetch URL, ищет `<script type="application/ld+json">` с `@type:"Recipe"`.
- Парсит `name, recipeIngredient[], nutrition{calories, fatContent, proteinContent, carbohydrateContent}`.
- Создаёт `Recipe` в базе, ингредиенты матчит к `Product` по имени (fuzzy search).
- В UI: кнопка «Импортировать рецепт» → форма с полем URL → предпросмотр → сохранить.

**Файлы:** `server.ts`, `schema.prisma` (добавить `Recipe`, `RecipeIngredient`)

---

### 3.2 Пользовательские рецепты (ручное создание)
**Что:** Создать рецепт вручную: название, фото, список ингредиентов из базы, количество порций. КБЖУ считается автоматически.  
**Почему:** Домашняя кухня. Пользователь один раз вводит рецепт борща — потом добавляет в дневник в 2 тапа.  
**Как:**
- Рецепт = набор `RecipeIngredient` (продукт + граммы) + `servings: Int`.
- КБЖУ рецепта = сумма КБЖУ всех ингредиентов / servings.
- `POST/GET /api/recipes`.
- В добавлении еды: отдельный таб «Рецепты» — список сохранённых рецептов + кнопка создать.

**Файлы:** `server.ts`, `schema.prisma`, `ClientApp.tsx`

## Спринт 4 — Экспорт, аналитика и CRM (приоритет: СРЕДНИЙ/НИЗКИЙ)

### 4.1 Экспорт личных данных
**Что:** `GET /api/export` возвращает zip с diary.json + custom_foods.json + weight_history.json.  
**Почему:** Пользователи больше доверяют приложению, из которого могут забрать свои данные. Обязательно для GDPR.  
**Как:** Собрать все записи пользователя, сериализовать в JSON, упаковать в zip (пакет `archiver`, MIT).

---

### 4.2 Аналитика за неделю/месяц
**Что:** Экран «Аналитика» — средние ккал и КБЖУ, сколько дней выполнена цель, тренды.  
**Почему:** Нутрициолог в CRM должен видеть прогресс клиента за период, а не листать день за днём.  
**Как:**
- `GET /api/analytics?userId=&startDate=&endDate=` — агрегирует диариEntries за период.
- Возвращает: `{ avgCalories, calGoalHitDays, avgProtein, avgFat, avgCarbs, weightTrend }`.
- В CRM: вкладка «Статистика» в профиле клиента.

---

### 4.3 Список покупок из плана питания (CRM)
**Что:** Нутрициолог составляет недельный план блюд для клиента → автоматически генерируется список покупок.  
**Почему:** Это главная ценность CRM для платящих нутрициологов.  
**Как:**
- `POST /api/meal-plans/:planId/shopping-list` — агрегирует ингредиенты всех блюд плана, суммирует дублирующиеся.
- Возвращает сгруппированный список: `{ category: string, items: { name, totalGrams }[] }[]`.
- В CRM: кнопка «Сгенерировать список покупок» → PDF или отправка на email клиента.
